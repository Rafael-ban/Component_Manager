# 扫码诊断与问题反馈

## 查询语言与备用来源

Android 根据设置中保存的应用语言选择站点：中文优先国内立创，英文优先国际
LCSC；Windows 跟随当前系统 UI 语言。首选站点成功后直接采用结果；遇到验证
拦截、网络错误、未匹配或响应异常才尝试备用站点，并在导入/批量结果中显示原因。
现有国际站公开页面适配器没有关键词搜索能力，英文模式的关键词查询会明确说明
使用国内搜索。站点验证并不等于二维码无法识别，也不会通过此改动绕过验证。

Android 不会长期缓存备用来源的结果来替代首选站点。切换应用语言会清理查询缓存，
保留库存；缓存本身也保留来源、参数、长描述和数据手册地址。

## 已知案例与判断边界

用户报告扫描后出现“无法识别 JLC 元件编号”。在 0.4.1 源码中，该文字来自
`JlcImportParser.parseText`；二维码解析入口的错误文字为“无法从二维码载荷中识别 JLC 料号”。
这两个错误发生在本地解析阶段，先于立创联网查询。浏览器能访问商城或调整代理，
都不能直接解释或修复这个解析错误。

本次提供的双二维码照片经本地 ZXing 解码，得到两个带大括号的单行载荷，长度为
83 和 81 字符，均有 `on,pc,pm,qty,mc,cc,pdi,hp` 字段，且 `pc` 均为合法 C 编号。
没有保存或提交真实订单字段、二维码原文或照片作为代码测试资源。
这验证了样例可解码、字段符合预期，并不等于复现了失败手机上的完整操作。
失败用户的安装版本和具体操作路径仍需核对。

## 反馈流程

Android 和 Windows 在设置中提供问题反馈。填写问题标题和复现描述后，可以选择附带
当前进程的诊断摘要，查看、修改内容，再打开 GitHub 新建 Issue 页面。
GitHub 登录与最终提交在系统浏览器中完成；应用不索取密码或保存 GitHub Token，
也不会在后台自动创建 Issue。反馈提交到公开仓库 `Rafael-ban/Component_Manager`。

诊断默认不附带。用户勾选后才将系统和应用版本及诊断内容加入报告；提交前应检查
自己填写的描述或截图是否包含不希望公开的信息。可以复制完整报告、导出文本，或清空日志。
较长报告超过预填 URL 的容量时，需要复制正文并在 GitHub 页面粘贴；不会默默截断日志。
导出的文本和截图可以由用户在 GitHub 编辑器中手动添加，应用不自动上传文件。

## 日志范围

诊断为本次进程内的有界事件记录，最多 100 条、16 KiB，重启应用后不保留。
它不是系统 Logcat、全部调试输出或用户数据库的副本。
事件以固定类型及数字字段记录扫码、解析和目录查询的阶段结果，例如解码候选数量、
图像尺寸、解析结果、HTTP 状态、超时、DNS 或 TLS 错误分类。
不默认记录原始二维码、订单、商品查询词、库存资料、同步服务器地址、Token、
任意异常消息或原始异常栈。无需为诊断上传真实标签照片。

遇到扫码问题时，请在失败后保持应用运行，打开反馈页附加诊断，并说明：

- 应用版本，以及错误发生在扫码结束后还是点击解析按钮后。
- 相机扫码或手动粘贴；画面中是否有多个二维码。
- 实际错误文字、预期行为和可重复的操作步骤。

商城验证页、空结果、响应结构变化和联网失败属于查询阶段，应与本地解析失败分别处理。
浏览器与应用的会话、Cookie 和连接环境可能不同，浏览器可访问并不保证应用请求成功。

0.4.2 的 `lookup_international success=true` 只说明解析未抛异常，可能仍未找到商品。
后续版本以 `matched=true/false` 区分实际匹配，并以 `cache=true/false` 标明缓存。
重复解析相同二维码也会重新触发受控查询，同时保留已补全信息和用户修改；旧请求
不能覆盖后来的输入。具体案例与批量流程见 [连续扫码入库](batch-jlc-inbound.md)。

GitHub URL 预填依据：[Creating an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue#creating-an-issue-from-a-url-query)。
完全在应用内提交需另行配置 GitHub OAuth/GitHub App，本版本不引入该授权流程。
